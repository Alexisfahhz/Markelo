Markelo, Token Architecture

This closes the audit gaps: a two-tier Variable structure, interaction states, focus ring, breakpoints, and grid. Everything here is anchored to the Design System PDF; derived values (interaction shades, ramp stops) are marked and tunable. The one rule that keeps the system consistent: components only ever bind to semantic tokens, never to a primitive directly.

The model

Two tiers: Primitives → Semantic

Primitives = the raw palette (blue/500 = #1A56A0). Never used in a design directly.  →  Semantic = named by job (action/primary = {blue/500}). This is what every button, card, and input binds to.
Why: when the brand blue changes, you edit one primitive and the whole system follows. When you add dark mode later, you add a mode to the semantic layer without renaming anything.

Monday morning · how to enter this in Figma

Variables build order

Create collection "Primitives", add every raw hex above as a colour variable, plus number variables for spacing (4→48), radius (4/8/12/100), and breakpoints. One mode: "Value".
Create collection "Semantic", add the semantic tokens, each set to alias its primitive (Figma: right-click value → “Create alias”). One mode: "Light" (adding "Dark" later needs no renames).
Create text styles from the 7-step scale (28/22/18/16/14/12/11), Plus Jakarta Sans, weights per the PDF.
Bind components to Semantic only. If you ever type a hex or pick a primitive inside a component, that's the bug, stop and alias instead. This single rule is what prevents the website inconsistency from recurring.
On Starter plan: Variables + styles work fine; you just can't publish a shared library. So keep every design file's components as instances of the master file, or design inside it. Decide this before Tuesday.
